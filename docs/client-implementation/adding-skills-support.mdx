本指南逐步说明如何为 AI 智能体或开发工具添加 Agent Skills 支持，覆盖技能的完整生命周期：发现技能、向模型说明技能、把技能内容加载到上下文，以及让这些内容在整个会话期间持续有效。

无论智能体采用何种架构，核心集成方式都相同。实现细节取决于两个因素：

- **技能存放在哪里？** 本地运行的智能体可以扫描用户文件系统中的技能目录。云托管或沙盒化智能体则需要其他发现机制，例如 API、远程注册表或附带资源。
- **模型如何访问技能内容？** 如果模型具备文件读取能力，它可以直接读取 `SKILL.md`。否则，你需要提供专用工具，或通过程序把技能内容注入提示词。

本指南会指出这些差异在何处产生影响。你无需支持所有场景，只需选择适合自己智能体的路径。

**前提条件**：熟悉 [Agent Skills 规范](/specification)，其中定义了 `SKILL.md` 文件格式、frontmatter 字段和目录约定。

## 核心原则：渐进式披露 [#the-core-principle-progressive-disclosure]

所有兼容技能的智能体都采用相同的三级加载策略：

| 层级    | 加载内容               | 加载时机   | Token 成本                 |
| ------- | ---------------------- | ---------- | -------------------------- |
| 1. 目录 | 名称 + 描述            | 会话开始时 | 每项技能约 50—100 个 token |
| 2. 指令 | 完整的 `SKILL.md` 正文 | 技能激活时 | 建议少于 5000 个 token     |
| 3. 资源 | 脚本、参考资料、素材   | 指令引用时 | 视情况而定                 |

模型从一开始就能看到技能目录，因此知道有哪些技能可用。当它判断某项技能与任务相关时，便加载完整指令。如果指令引用了支持文件，模型会根据需要逐个加载。

这种方式既保持了较小的基础上下文，又让模型能够按需访问专业知识。即使智能体安装了 20 项技能，也无需预先承担 20 份完整指令的 token 成本，只需为当前对话实际使用的技能付出成本。

## 步骤 1：发现技能 [#step-1-discover-skills]

会话启动时，查找所有可用技能并加载其元数据。

### 扫描位置 [#where-to-scan]

扫描哪些目录取决于智能体的运行环境。大多数本地运行的智能体至少会扫描两个作用域：

- **项目级**（相对于工作目录）：特定于某个项目或仓库的技能。
- **用户级**（相对于主目录）：指定用户在所有项目中都可用的技能。

也可以采用其他作用域，例如由管理员部署的组织级技能，或智能体自身附带的技能。应根据智能体的部署模式选择合适的作用域集合。

在每个作用域中，可以同时扫描一个**客户端特定目录**和约定的 **`.agents/skills/` 目录**：

| 作用域 | 路径                               | 用途             |
| ------ | ---------------------------------- | ---------------- |
| 项目   | `<project>/.<your-client>/skills/` | 客户端的原生位置 |
| 项目   | `<project>/.agents/skills/`        | 跨客户端互操作   |
| 用户   | `~/.<your-client>/skills/`         | 客户端的原生位置 |
| 用户   | `~/.agents/skills/`                | 跨客户端互操作   |

`.agents/skills/` 路径已经成为跨客户端共享技能的广泛采用约定。Agent Skills 规范并不规定技能目录必须存放在哪里（它只定义目录内部的内容），但扫描 `.agents/skills/` 可以让其他兼容客户端安装的技能自动对你的客户端可见，反之亦然。

<Note>
  为了实现务实的兼容性，一些实现还会同时扫描项目级和用户级的
  `.claude/skills/`，因为许多现有技能安装在那里。其他附加位置包括直至 Git 根目录的祖先目录（适用于
  monorepo）、[XDG](https://specifications.freedesktop.org/basedir-spec/latest/)
  配置目录，以及用户配置的路径。
</Note>

### 扫描目标 [#what-to-scan-for]

在每个技能目录内，查找**包含一个名称恰好为 `SKILL.md` 的文件的子目录**：

```
~/.agents/skills/
├── pdf-processing/
│   ├── SKILL.md          ← 已发现
│   └── scripts/
│       └── extract.py
├── data-analysis/
│   └── SKILL.md          ← 已发现
└── README.md             ← 忽略（不是技能目录）
```

实用的扫描规则：

- 跳过不会包含技能的目录，例如 `.git/` 和 `node_modules/`
- 可以选择遵循 `.gitignore`，避免扫描构建产物
- 设置合理边界（例如最大深度 4—6 层、最多 2000 个目录），防止在大型目录树中失控扫描

### 处理名称冲突 [#handling-name-collisions]

如果两项技能具有相同的 `name`，应采用确定性的优先级规则。

现有实现普遍遵循的约定是：**项目级技能覆盖用户级技能。**

在同一作用域内（例如 `<project>/.agents/skills/` 和 `<project>/.<your-client>/skills/` 中都发现名为 `code-review` 的技能），先发现优先或后发现优先都可以，但必须选定一种并保持一致。发生冲突时应记录警告，让用户知道某项技能被遮蔽。

### 信任考量 [#trust-considerations]

项目级技能来自当前处理的仓库，而该仓库可能不受信任，例如刚刚克隆的开源项目。可以考虑让项目级技能的加载受信任检查控制：只有当用户把项目文件夹标记为可信时才加载。这样可以防止不受信任的仓库悄悄向智能体上下文注入指令。

### 云托管和沙盒化智能体 [#cloud-hosted-and-sandboxed-agents]

如果智能体在容器或远程服务器中运行，就无法访问用户的本地文件系统。发现机制需要根据技能作用域采用不同方式：

- **项目级技能**通常最容易处理。如果智能体操作的是克隆仓库（即使位于沙盒内），项目级技能会随代码一起存在，可以从仓库目录树中扫描。
- **用户级和组织级技能**不存在于沙盒中。需要从外部来源进行配置，例如克隆配置仓库、通过智能体设置接收技能 URL 或软件包，或者允许用户通过 Web UI 上传技能目录。
- **内置技能**可以作为静态资源打包进智能体的部署产物，使其无需外部获取即可用于每个会话。

技能可供智能体访问后，后续生命周期（解析、披露和激活）的工作方式都相同。

## 步骤 2：解析 `SKILL.md` 文件 [#step-2-parse-skillmd-files]

针对每个发现的 `SKILL.md`，提取元数据和正文内容。

### 提取 frontmatter [#frontmatter-extraction]

一个 `SKILL.md` 文件包含两部分：位于 `---` 分隔符之间的 YAML frontmatter，以及结束分隔符之后的 Markdown 正文。解析步骤如下：

1. 找到文件开头的 `---`，以及位于其后的结束 `---`。
2. 解析两者之间的 YAML 块。提取必需的 `name` 和 `description`，以及所有可选字段。
3. 结束 `---` 之后的全部内容在去除首尾空白后，即为技能正文。

frontmatter 字段的完整集合及其约束，请参阅[规范](/specification)。

### 处理格式错误的 YAML [#handling-malformed-yaml]

为其他客户端编写的技能文件可能包含严格来说无效、但恰好被其解析器接受的 YAML。最常见的问题是未加引号的值中包含冒号：

```yaml
# 严格来说是无效 YAML——冒号会导致解析失败
description: 在以下情况下使用此技能：用户询问 PDF
```

可以考虑添加回退机制：先把这类值用引号包裹，或转换成 YAML 块标量，然后重试解析。这样只需很低的成本即可改善跨客户端兼容性。

### 宽松验证 [#lenient-validation]

遇到问题时发出警告，但只要可能仍然加载技能：

- 名称与父目录名称不一致 → 警告，但仍加载
- 名称超过 64 个字符 → 警告，但仍加载
- 缺少描述或描述为空 → 跳过技能并记录错误（描述是披露技能的必要信息）
- YAML 完全无法解析 → 跳过技能并记录错误

记录诊断信息，以便通过调试命令、日志文件或 UI 向用户展示，但不要因为表面问题阻止技能加载。

<Note>
  [规范](/specification)对 `name`
  字段定义了严格约束（与父目录一致、字符集、最大长度）。上面的宽松方式有意放宽这些约束，以提高与其他客户端所编写技能的兼容性。
</Note>

### 存储内容 [#what-to-store]

每条技能记录至少需要三个字段：

| 字段          | 说明                      |
| ------------- | ------------------------- |
| `name`        | 来自 frontmatter          |
| `description` | 来自 frontmatter          |
| `location`    | `SKILL.md` 文件的绝对路径 |

将这些记录存储在以 `name` 为键的内存映射中，以便激活时快速查找。

还可以在发现时存储技能**正文**（frontmatter 之后的 Markdown 内容），或者在激活时从 `location` 读取。存储正文可以加快激活；在激活时读取则减少整体内存用量，并能获取两次激活之间对技能文件所做的修改。

之后解析相对路径和枚举附带资源时，需要技能的**基础目录**（`location` 的父目录）。可以在需要时从 `location` 推导。

## 步骤 3：向模型披露可用技能 [#step-3-disclose-available-skills-to-the-model]

告诉模型存在哪些技能，但不加载完整内容。这是[渐进式披露的第 1 层](#the-core-principle-progressive-disclosure)。

### 构建技能目录 [#building-the-skill-catalog]

针对每个已发现技能，使用适合技术栈的结构化格式包含 `name`、`description` 和可选的 `location`（`SKILL.md` 文件路径）。XML、JSON 或项目符号列表都可以：

```xml
<available_skills>
  <skill>
    <name>pdf-processing</name>
    <description>提取 PDF 文本、填写表单并合并文件。处理 PDF 时使用。</description>
    <location>/home/user/.agents/skills/pdf-processing/SKILL.md</location>
  </skill>
  <skill>
    <name>data-analysis</name>
    <description>分析数据集、生成图表并创建摘要报告。</description>
    <location>/home/user/project/.agents/skills/data-analysis/SKILL.md</location>
  </skill>
</available_skills>
```

`location` 字段有两个用途：支持文件读取激活（参见[步骤 4](#step-4-activate-skills)），以及为模型提供基础路径，用于解析技能正文中的相对引用（例如 `scripts/evaluate.py`）。如果专用激活工具会在结果中提供技能目录路径（参见步骤 4 的[结构化包装](#structured-wrapping)），则可以从目录中省略 `location`；否则应包含该字段。

每项技能会为目录增加约 50—100 个 token。即使安装了数十项技能，目录仍然很紧凑。

### 放置技能目录的位置 [#where-to-place-the-catalog]

常见方式有两种：

**系统提示词章节**：将目录作为带标签的章节添加到系统提示词中，并在前面用简短指令说明如何使用技能。这是最简单的方式，适用于任何能使用文件读取工具的模型。

**工具描述**：把目录嵌入专用技能激活工具的描述中（参见[步骤 4](#step-4-activate-skills)）。这样可以保持系统提示词整洁，并让发现与激活自然结合。

两种方式都能工作。把目录放入系统提示词更简单、兼容性更广；如果已有专用激活工具，嵌入工具描述会更整洁。

### 行为指令 [#behavioral-instructions]

在目录旁加入一段简短指令，告诉模型如何以及何时使用技能。措辞取决于所支持的激活机制（参见[步骤 4](#step-4-activate-skills)）：

**如果模型通过读取文件激活技能：**

```
以下技能为特定任务提供专业指令。
当任务与某项技能的描述匹配时，请先使用文件读取工具加载所列位置的
SKILL.md，然后再继续。
如果技能引用相对路径，请以技能目录（SKILL.md 的父目录）为基准解析，
并在工具调用中使用绝对路径。
```

**如果模型通过专用工具激活技能：**

```
以下技能为特定任务提供专业指令。
当任务与某项技能的描述匹配时，使用技能名称调用 activate_skill 工具，
加载完整指令。
```

这些指令应保持简洁。目标只是告诉模型技能的存在和加载方式；技能激活后，技能内容本身会提供详细指令。

### 筛选 [#filtering]

某些技能不应出现在目录中，常见原因包括：

- 用户在设置中禁用了技能
- 权限系统拒绝访问技能
- 技能选择不由模型驱动激活（例如通过 `disable-model-invocation` 标志）

应从目录中**完全隐藏被筛选的技能**，而不是列出后再在激活时阻止。这样可以避免模型浪费轮次尝试加载无法使用的技能。

### 没有可用技能时 [#when-no-skills-are-available]

如果没有发现技能，请完全省略目录和行为指令。不要显示空的 `<available_skills/>` 块，也不要注册没有有效选项的技能工具，否则会让模型困惑。

## 步骤 4：激活技能 [#step-4-activate-skills]

当模型或用户选择技能时，把完整指令传入对话上下文。这是[渐进式披露的第 2 层](#the-core-principle-progressive-disclosure)。

### 模型驱动激活 [#model-driven-activation]

大多数实现依靠模型自行判断是否激活，而不是在运行环境一侧实现触发匹配或关键词检测。模型读取目录（来自[步骤 3](#step-3-disclose-available-skills-to-the-model)），判断某项技能与当前任务相关，然后加载技能。

有两种实现模式：

**文件读取激活**：模型使用标准文件读取工具，读取目录中列出的 `SKILL.md` 路径。无需特殊基础设施，智能体现有的文件读取能力就足够。模型会以工具结果的形式接收文件内容。如果模型拥有文件访问权限，这是最简单的方式。

**专用工具激活**：注册一个接收技能名称并返回内容的工具，例如 `activate_skill`。当模型无法直接读取文件时必须采用此方式；即使模型可以读取文件，这种方式也可以选择使用，而且很有帮助。相较直接读取原始文件，它有以下优点：

- 控制返回内容，例如剥离或保留 YAML frontmatter（参见下文[模型接收的内容](#what-the-model-receives)）
- 使用结构化标签包装内容，以便在上下文管理期间识别
- 在指令旁列出附带资源（例如 `references/*`）
- 实施权限控制或请求用户同意
- 跟踪激活情况，用于分析

<Tip>
  使用专用激活工具时，请把 `name`
  参数限制为有效技能名称集合，例如在工具模式中使用枚举。这样可以防止模型虚构不存在的技能名称。如果没有可用技能，则完全不要注册该工具。
</Tip>

### 用户显式激活 [#user-explicit-activation]

用户也应该能直接激活技能，而无需等待模型决定。最常见的模式是由运行环境拦截的**斜杠命令或提及语法**（`/skill-name` 或 `$skill-name`）。具体语法由你决定；关键是由运行环境负责查找和注入，使模型无需自行执行激活动作就能收到技能内容。

自动补全组件（在用户输入时列出可用技能）也能提高该功能的可发现性。

### 模型接收的内容 [#what-the-model-receives]

技能激活时，模型会收到技能指令。具体内容有两种选择：

**完整文件**：模型看到整个 `SKILL.md`，包括 YAML frontmatter。这是文件读取激活的自然结果，因为模型读取的是原始文件；对于专用工具而言也是有效选择。frontmatter 可能包含激活时有用的字段，例如 [`compatibility`](/specification#compatibility-field) 会说明环境要求，并影响模型执行技能指令的方式。

**仅正文（剥离 frontmatter）**：运行环境解析并删除 YAML frontmatter，只返回 Markdown 指令。在使用专用激活工具的现有实现中，大多数采用这种方式：发现阶段提取 `name` 和 `description` 后剥离 frontmatter。

两种方式在实践中都能工作。

### 结构化包装 [#structured-wrapping]

如果使用专用激活工具，可以考虑用标识标签包装技能内容。例如：

```xml
<skill_content name="pdf-processing">
# PDF 处理

## 何时使用此技能
当用户需要处理 PDF 文件时使用此技能……

[SKILL.md 正文的其余部分]

技能目录：/home/user/.agents/skills/pdf-processing
此技能中的相对路径均相对于技能目录。

<skill_resources>
  <file>scripts/extract.py</file>
  <file>scripts/merge.py</file>
  <file>references/pdf-spec-summary.md</file>
</skill_resources>
</skill_content>
```

这样做有几个实际好处：

- 模型可以清楚地区分技能指令和其他对话内容
- 运行环境能在上下文压缩期间识别并保留技能内容（[步骤 5](#step-5-manage-skill-context-over-time)）
- 无需提前加载，即可向模型展示附带资源

### 列出附带资源 [#listing-bundled-resources]

专用激活工具返回技能内容时，还可以枚举技能目录中的支持文件（脚本、参考资料、素材），但**不应提前读取**。当技能指令引用这些文件时，模型会按需使用文件读取工具加载特定文件。

对于大型技能目录，可以限制列表长度，并注明列表可能不完整。

### 权限允许列表 [#permission-allowlisting]

如果智能体使用权限系统控制文件访问，请将**技能目录加入允许列表**，使模型无需触发用户确认提示即可读取附带资源。否则，每次引用附带脚本或参考文件都会弹出权限对话框，破坏包含 `SKILL.md` 之外资源的技能工作流。

## 步骤 5：长期管理技能上下文 [#step-5-manage-skill-context-over-time]

技能指令进入对话上下文后，应让其在整个会话期间持续有效。

### 保护技能内容不被上下文压缩移除 [#protect-skill-content-from-context-compaction]

如果智能体会在上下文窗口填满时截断或总结较早的消息，请**免除技能内容的剪枝**。技能指令是需要长期保留的行为指导；如果它们在对话中途丢失，智能体性能会悄悄下降，却不会出现任何可见错误。模型会继续工作，但已失去技能所提供的专业指令。

常见方式包括：

- 将技能工具输出标记为受保护内容，使剪枝算法跳过
- 使用步骤 4 中的[结构化标签](#structured-wrapping)识别技能内容，并在压缩期间保留

### 激活去重 [#deduplicate-activations]

可以跟踪当前会话中已激活的技能。如果模型或用户尝试加载已经存在于上下文中的技能，可以跳过再次注入，避免相同指令在对话中重复出现。

### 委派给子智能体（可选） [#subagent-delegation-optional]

这是一种只有部分客户端支持的高级模式。技能指令不会注入主对话，而是在**独立的子智能体会话**中运行。子智能体接收技能指令、执行任务，再把工作摘要返回主对话。

当技能工作流非常复杂，适合使用专用且聚焦的会话时，这种模式很有用。
