技能只有在被激活时才能发挥作用。`SKILL.md` frontmatter 中的 `description` 字段，是智能体判断是否需要为给定任务加载技能的主要依据。描述不够具体，技能就不会在应该触发时触发；描述过于宽泛，技能又会在不该触发时触发。

本指南介绍如何系统测试并改进技能描述，以提高触发准确性。

## 技能触发的工作方式 [#how-skill-triggering-works]

智能体使用[渐进式披露（progressive disclosure）](/specification#progressive-disclosure)管理上下文。启动时，它只加载每个可用技能的 `name` 和 `description`，这些信息刚好足以判断技能何时可能相关。当用户的任务与某项描述匹配时，智能体会把完整的 `SKILL.md` 读入上下文并遵循其中的指令。

这意味着描述承担了触发技能的全部责任。如果描述没有表达清楚技能何时有用，智能体就不知道应该使用它。

这里有一个重要细节：通常只有当任务所需的知识或能力超出智能体独立处理的范围时，智能体才会查阅技能。即使描述完全匹配，“读取这个 PDF”这样的简单单步请求也可能不会触发 PDF 技能，因为智能体能够用基本工具完成。涉及专业知识的任务，例如陌生的 API、领域特定工作流或不常见的格式，才是优质描述能够产生明显影响的地方。

## 编写有效描述 [#writing-effective-descriptions]

开始测试前，先了解优质描述的特点会很有帮助。基本原则如下：

- **使用祈使语气。** 把描述写成对智能体的指令，例如使用“在……时使用此技能”，而不是“此技能会……”。智能体正在决定是否采取行动，因此应直接告诉它何时行动。
- **聚焦用户意图，而非实现方式。** 描述用户想要实现什么，不要描述技能的内部机制。智能体会根据用户提出的要求进行匹配。
- **宁可更主动一些。** 明确列出技能适用的情境，包括用户没有直接说出领域名称的情况，例如“即使用户没有明确提到‘CSV’或‘分析’也应使用”。
- **保持简洁。** 几句话到一个短段落通常最合适：既足以覆盖技能范围，又不会在存在大量技能时过度占用智能体上下文。[规范](/specification#description-field)规定了 1024 个字符的硬性上限。

## 设计触发评估查询 [#designing-trigger-eval-queries]

要测试触发行为，需要准备一组评估查询：为真实的用户提示词标注它们是否应该触发技能。

```json eval_queries.json
[
  {
    "query": "我在 ~/data/q4_results.xlsx 有一个表格，C 列是收入，D 列是支出——能否添加利润率列，并突出显示低于 10% 的项目？",
    "should_trigger": true
  },
  { "query": "把这个 json 文件转成 yaml 最快的方法是什么", "should_trigger": false }
]
```

目标是准备约 20 条查询：8—10 条应该触发，另有 8—10 条不应该触发。

### 应触发查询 [#should-trigger-queries]

这些查询用于测试描述是否覆盖了技能范围。请沿多个维度制造变化：

- **措辞**：既有正式表达，也有口语表达，并加入一些拼写错误或缩写。
- **明确程度**：有些直接说出技能领域（“分析这个 CSV”），另一些只描述需求而不点明领域（“老板想让我根据这个数据文件制作一张图表”）。
- **详细程度**：把简短提示词和上下文丰富的提示词混合起来，例如简短的“分析销售 CSV 并制作图表”，以及包含文件路径、列名和背景信息的较长消息。
- **复杂程度**：改变步骤和决策点的数量。既包含单步任务，也包含多步骤工作流，以测试智能体能否在较长的任务链中发现技能的相关性。

最有价值的应触发查询，是技能确实能提供帮助、但从查询表面看关联并不明显的查询。在这些情况下，描述措辞会产生真正的影响；如果查询已经明确要求技能所做的事情，那么任何合理的描述都能触发。

### 不应触发查询 [#should-not-trigger-queries]

最有价值的负面测试用例是**近似但不匹配的情况**：它们与技能共享关键词或概念，但实际需要其他能力。这类查询测试的是描述是否精准，而不仅是是否宽泛。

对于 CSV 分析技能，较弱的负面示例包括：

- `"编写一个斐波那契函数"`——显然无关，没有测试价值。
- `"今天天气怎么样？"`——没有重叠关键词，过于简单。

较强的负面示例包括：

- `"我需要更新 Excel 预算表中的公式"`——共享“表格”和“数据”等概念，但需要的是 Excel 编辑，而非 CSV 分析。
- `"能否编写一个 python 脚本，读取 csv 并把每一行上传到 postgres 数据库"`——虽然涉及 CSV，但任务属于数据库 ETL，而非分析。

### 提升真实性的技巧 [#tips-for-realism]

真实用户提示词包含通用测试查询所缺少的上下文。请加入：

- 文件路径（`~/Downloads/report_final_v2.xlsx`）
- 个人背景（`"我的经理让我……"`）
- 具体细节（列名、公司名称、数据值）
- 口语、缩写和偶尔的拼写错误

## 测试描述是否触发 [#testing-whether-a-description-triggers]

基本方法是：安装技能后，让智能体逐条处理查询，并观察它是否调用技能。请确保技能已经注册并且能被智能体发现；不同客户端的实现方式不同，例如使用技能目录、配置文件或 CLI 标志。

大多数智能体客户端都提供某种可观测信息，例如执行日志、工具调用历史或详细输出，让你能够查看运行期间查阅了哪些技能。如果智能体加载了技能的 `SKILL.md`，说明技能已触发；如果智能体没有查阅技能就继续处理，则说明没有触发。具体细节请查阅客户端文档。

查询在以下情况下“通过”：

- `should_trigger` 为 `true`，并且技能已调用；或者
- `should_trigger` 为 `false`，并且技能未调用。

### 多次运行 [#running-multiple-times]

模型行为具有非确定性：同一条查询可能在一次运行中触发技能，在另一次运行中却不触发。请多次运行每条查询（3 次是合理起点），并计算**触发率**，即技能被调用的运行次数占比。

如果应触发查询的触发率高于阈值（0.5 是合理默认值），则该查询通过；如果不应触发查询的触发率低于阈值，则该查询通过。

20 条查询各运行 3 次，共需调用 60 次，因此最好编写脚本。下面展示了通用结构；请把 `claude` 调用和 `check_triggered` 中的检测逻辑替换为智能体客户端提供的机制：

```bash
#!/bin/bash
QUERIES_FILE="${1:?用法：$0 <queries.json>}"
SKILL_NAME="my-skill"
RUNS=3

# 此示例使用 Claude Code 的 JSON 输出检查 Skill 工具调用。
# 请将此函数替换为适用于你的智能体客户端的检测逻辑。
# 如果技能被调用，应返回 0（成功）；否则返回 1。
check_triggered() {
  local query="$1"
  claude -p "$query" --output-format json 2>/dev/null \
    | jq -e --arg skill "$SKILL_NAME" \
      'any(.messages[].content[]; .type == "tool_use" and .name == "Skill" and .input.skill == $skill)' \
      > /dev/null 2>&1
}

count=$(jq length "$QUERIES_FILE")
for i in $(seq 0 $((count - 1))); do
  query=$(jq -r ".[$i].query" "$QUERIES_FILE")
  should_trigger=$(jq -r ".[$i].should_trigger" "$QUERIES_FILE")
  triggers=0

  for run in $(seq 1 $RUNS); do
    check_triggered "$query" && triggers=$((triggers + 1))
  done

  jq -n \
    --arg query "$query" \
    --argjson should_trigger "$should_trigger" \
    --argjson triggers "$triggers" \
    --argjson runs "$RUNS" \
    '{query: $query, should_trigger: $should_trigger, triggers: $triggers, runs: $runs, trigger_rate: ($triggers / $runs)}'
done | jq -s '.'
```

<Tip>
  如果智能体客户端支持，可以在结果已经明确后提前停止运行：智能体要么查阅了技能，要么已经在未使用技能的情况下开始工作。这能显著减少运行完整评估集所需的时间和成本。
</Tip>

## 使用训练集/验证集拆分避免过拟合 [#avoiding-overfitting-with-trainvalidation-splits]

如果使用全部查询优化描述，就有过拟合的风险：得到的描述可能适用于这些特定措辞，却无法适用于新查询。

解决方法是拆分查询集：

- **训练集（约 60%）**：用于识别失败并指导改进的查询。
- **验证集（约 40%）**：暂时保留，只用于检查改进能否泛化的查询。

请确保两个集合都按比例混合了应触发和不应触发查询，不要意外地把所有正面用例都放进同一个集合。随机打乱，并在各轮迭代中保持拆分不变，这样比较结果才具有一致的基准。

如果使用类似[上文](#running-multiple-times)的脚本，可以把查询拆分到 `train_queries.json` 和 `validation_queries.json` 两个文件中，再分别对两个文件运行脚本。

## 优化循环 [#the-optimization-loop]

1. 在*训练集和验证集*上**评估**当前描述。训练集结果用于指导修改；验证集结果用于判断修改能否泛化。
2. **识别训练集中的失败**：哪些应触发查询没有触发？哪些不应触发查询却触发了？
   - 只使用训练集中的失败指导修改。无论是自行修改描述，还是提示 LLM 进行修改，都不要把验证集结果引入该过程。
3. **修改描述。** 聚焦泛化能力：
   - 如果应触发查询失败，描述可能过窄。扩大范围，或补充说明技能何时有用。
   - 如果不应触发查询发生误触发，描述可能过宽。具体说明技能*不做什么*，或明确此技能与相邻能力的边界。
   - 不要直接加入失败查询中的特定关键词，否则会造成过拟合。应找到这些查询所代表的一般类别或概念，再处理该类别。
   - 如果多次迭代后仍没有进展，请尝试采用结构完全不同的描述方式，而不是继续微调。不同的框架或句子结构，可能会突破细节优化无法解决的问题。
   - 检查描述是否始终低于 1024 个字符的上限，因为描述往往会在优化过程中不断变长。
4. **重复**步骤 1—3，直到训练集中的所有查询都通过，或者已经没有明显改进。
5. 根据验证通过率，即*验证集*中通过查询的比例，**选择最佳迭代**。最佳描述不一定是最后生成的描述；早期迭代的验证通过率可能高于后续对训练集过拟合的版本。

通常五轮迭代就足够了。如果性能没有改善，问题可能出在查询上（过于简单、过于困难或标签有误），而不是描述本身。

<Tip>
  [`skill-creator`](https://github.com/anthropics/skills/tree/main/skills/skill-creator)
  技能可以端到端自动执行此循环：拆分评估集、并行评估触发率、使用 Claude
  提出描述改进建议，并生成可在运行时实时查看的 HTML 报告。
</Tip>

## 应用结果 [#applying-the-result]

选出最佳描述后：

1. 更新 `SKILL.md` frontmatter 中的 `description` 字段。
2. 验证描述未超过 [1024 个字符的上限](/specification#description-field)。
3. 验证描述能否按预期触发。手动尝试几条提示词，快速做一次健全性检查。如需更严格的测试，请编写 5—10 条全新查询（混合应触发和不应触发查询），并用评估脚本运行。由于这些查询从未参与优化过程，因此可以诚实检验描述能否泛化。

修改前后对比：

```yaml
# 修改前
description: 处理 CSV 文件。

# 修改后
description: >
  分析 CSV 和表格数据文件：计算汇总统计、添加派生列、生成图表并清理混乱数据。
  当用户拥有 CSV、TSV 或 Excel 文件，并希望探索、转换或可视化数据时使用此技能，
  即使他们没有明确提到“CSV”或“分析”。
```

改进后的描述更具体地说明了技能的作用（汇总统计、派生列、图表和清理），也更广泛地说明了适用情形（CSV、TSV 和 Excel，即使没有明确的关键词）。
