## 从真实专业知识出发 [#start-from-real-expertise]

创建技能时，一个常见误区是让 LLM 在没有领域特定上下文的情况下生成技能，完全依赖 LLM 的通用训练知识。结果往往是模糊、泛化的流程（例如“妥善处理错误”“遵循身份验证最佳实践”），而不是让技能真正有价值的具体 API 模式、边界情况和项目约定。

有效的技能以真实专业知识为基础。关键在于把领域特定的上下文引入创建过程。

### 从实际任务中提炼 [#extract-from-a-hands-on-task]

在与智能体的对话中完成一个真实任务，并在过程中提供上下文、纠正和偏好。然后把其中可复用的模式提炼成技能。请特别留意：

- **行之有效的步骤**——最终取得成功的操作顺序
- **你做出的纠正**——你调整智能体方法的地方（例如“使用库 X 而不是 Y”“检查边界情况 Z”）
- **输入/输出格式**——输入和输出数据的具体形态
- **你提供的上下文**——智能体原本不知道的项目特定事实、约定或约束

### 从现有项目资料中归纳 [#synthesize-from-existing-project-artifacts]

如果已经积累了一批知识资料，可以将其提供给 LLM，让它归纳出技能。根据团队真实事故报告和运行手册归纳的数据流水线技能，会优于根据泛泛的“数据工程最佳实践”文章生成的技能，因为前者包含*你的*模式、故障类型和恢复流程。关键在于使用项目特定资料，而非通用参考。

优质的来源资料包括：

- 内部文档、运行手册和风格指南
- API 规范、模式和配置文件
- 代码审查意见和问题跟踪记录（能够反映反复出现的问题和审查者的预期）
- 版本控制历史，尤其是补丁和修复（实际发生的变更会揭示规律）
- 真实故障案例及其解决方案

## 通过实际执行持续改进 [#refine-with-real-execution]

技能的初稿通常需要改进。请让技能处理真实任务，再把所有结果（不只是失败结果）反馈到创建过程中。思考：什么触发了误报？遗漏了什么？哪些内容可以删减？

即便只执行一轮“运行后修订”，质量通常也会明显提高；复杂领域往往能从多轮迭代中受益。

<Tip>
请阅读智能体的执行轨迹，而不仅是最终输出。如果智能体在无效步骤上浪费时间，常见原因包括：指令过于模糊（智能体在找到有效方法前尝试了多种方案）、指令不适用于当前任务（智能体仍然照做），或者给出了太多选项却没有明确的默认选择。
</Tip>

如需采用包含测试用例、断言和评分的结构化迭代方法，请参阅[评估技能输出质量](/skill-creation/evaluating-skills)。

## 明智使用上下文 [#spending-context-wisely]

技能激活后，其 `SKILL.md` 正文会与对话历史、系统上下文和其他已激活技能一起完整加载到智能体的上下文窗口中。技能里的每个 token 都在与窗口内的其他内容争夺智能体的注意力。

### 补充智能体欠缺的内容，省略它已知的内容 [#add-what-the-agent-lacks-omit-what-it-knows]

应聚焦于智能体在没有此技能时*不会*知道的内容：项目特定约定、领域特定流程、不明显的边界情况，以及需要使用的特定工具或 API。无需解释什么是 PDF、HTTP 如何工作或数据库迁移的作用。

````markdown
<!-- 过于冗长——智能体已经知道 PDF 是什么 -->
## 提取 PDF 文本

PDF（便携式文档格式）文件是一种常见文件格式，其中包含文本、
图像和其他内容。要从 PDF 中提取文本，需要使用一个库。
推荐使用 pdfplumber，因为它能够妥善处理大多数情况。

<!-- 更好——直接说明智能体自身不知道的内容 -->
## 提取 PDF 文本

使用 pdfplumber 提取文本。对于扫描文档，回退到
pdf2image 和 pytesseract。

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
````

针对每段内容问自己：“如果没有这条指令，智能体会做错吗？”如果答案是否定的，就删掉。如果不确定，就进行测试。如果智能体没有技能也能很好地完成整个任务，那么该技能可能没有带来价值。有关如何系统测试这一点，请参阅[评估技能输出质量](/skill-creation/evaluating-skills)。

### 设计连贯的工作单元 [#design-coherent-units]

确定技能的覆盖范围，就像确定函数的职责：它应该封装一个连贯的工作单元，并能与其他技能良好组合。范围太窄会迫使单个任务加载多个技能，带来额外开销和指令冲突的风险；范围太宽则难以精确激活。查询数据库并格式化结果可以是一个连贯的技能，而再把数据库管理纳入其中，可能就承担得太多了。

### 保持适度的细节 [#aim-for-moderate-detail]

过于全面的技能可能弊大于利：智能体难以提取相关信息，还可能因为不适用于当前任务的指令而走上无效路径。简洁的分步指导加上一个可运行示例，通常优于面面俱到的文档。当你试图覆盖每个边界情况时，请考虑其中大多数情况是否更适合交由智能体自行判断。

### 用渐进式披露组织大型技能 [#structure-large-skills-with-progressive-disclosure]

[规范](/specification#progressive-disclosure)建议将 `SKILL.md` 控制在 500 行和 5,000 个 token 以内，只保留智能体每次运行都需要的核心指令。如果技能确实需要更多内容，请把详细参考资料移到 `references/` 或类似目录下的独立文件中。

关键是告诉智能体*何时*加载每个文件。“如果 API 返回非 200 状态码，请读取 `references/api-errors.md`”比泛泛的“详情见 references/”更有用。这样智能体就能按需加载上下文，而不是提前全部加载；这正是[渐进式披露](/specification#progressive-disclosure)的设计方式。

## 调整控制程度 [#calibrating-control]

技能的各个部分不需要采用相同的规定强度。请让指令的具体程度与任务的脆弱程度相匹配。

### 让具体程度与脆弱程度匹配 [#match-specificity-to-fragility]

当多种方法都有效且任务允许变化时，**给予智能体自由**。对于灵活的指令，解释*原因*可能比僵硬的命令更有效——理解指令目的的智能体能够根据上下文做出更好的决定。代码审查技能可以说明要检查什么，而不规定精确步骤：

```markdown
## 代码审查流程

1. 检查所有数据库查询是否存在 SQL 注入（使用参数化查询）
2. 验证每个端点上的身份验证检查
3. 查找并发代码路径中的竞态条件
4. 确认错误消息不会泄露内部细节
```

当操作脆弱、结果必须一致或必须遵循特定顺序时，**给出明确规定**：

````markdown
## 数据库迁移

严格按照以下顺序运行：

```bash
python scripts/migrate.py --verify --backup
```

不要修改命令或添加其他标志。
````

大多数技能会混合使用这两种方式。请分别调整每个部分。

### 提供默认方案，而不是选项菜单 [#provide-defaults-not-menus]

如果有多种可用工具或方法，请选择一个默认方案，并简要提及替代方案，而不是把它们作为同等选项罗列出来。

````markdown
<!-- 选项过多 -->
你可以使用 pypdf、pdfplumber、PyMuPDF 或 pdf2image……

<!-- 默认方案明确，同时保留备用路径 -->
使用 pdfplumber 提取文本：

```python
import pdfplumber
```

对于需要 OCR 的扫描 PDF，改用 pdf2image 和 pytesseract。
````

### 优先编写流程，而非声明 [#favor-procedures-over-declarations]

技能应该教智能体*如何处理*一类问题，而不是告诉它为某个具体实例*生成什么*。请比较：

```markdown
<!-- 具体答案——只对这一项任务有用 -->
通过 `customer_id` 连接 `orders` 表和 `customers` 表，筛选
`region = 'EMEA'` 的记录，并对 `amount` 列求和。

<!-- 可复用方法——适用于任何分析查询 -->
1. 从 `references/schema.yaml` 读取模式，找到相关表
2. 按照 `_id` 外键约定连接表
3. 将用户请求中的所有筛选条件应用为 WHERE 子句
4. 按需聚合数值列，并格式化为 Markdown 表格
```

这并不表示技能不能包含具体细节：输出格式模板（参见[输出格式模板](#templates-for-output-format)）、“绝不输出 PII”等约束和工具特定指令都很有价值。重点是，即使各项细节很具体，整体*方法*也应该能够泛化。

## 有效指令的模式 [#patterns-for-effective-instructions]

以下是组织技能内容的可复用技巧。并非每个技能都需要全部使用，请选择适合任务的模式。

### 易错点章节 [#gotchas-sections]

在许多技能中，价值最高的内容是一份易错点列表，也就是那些违背合理假设的环境特定事实。这些不是“妥善处理错误”之类的泛泛建议，而是对智能体在缺少说明时会犯下的错误做出的具体纠正：

````markdown
## 易错点

- `users` 表使用软删除。查询必须包含
  `WHERE deleted_at IS NULL`，否则结果会包括已停用的账户。
- 用户 ID 在数据库中是 `user_id`，在身份验证服务中是 `uid`，
  在计费 API 中是 `accountId`。这三个名称指的是同一个值。
- 只要 Web 服务器仍在运行，`/health` 端点就会返回 200，
  即使数据库连接已经中断。请使用 `/ready` 检查完整服务状态。
````

应把易错点放在 `SKILL.md` 中，以便智能体在遇到相应情况前就读到它们。如果明确告诉智能体何时加载，单独的参考文件也可以使用；但对于不明显的问题，智能体可能无法识别触发条件。

<Tip>
当智能体犯错而你需要纠正时，请把纠正内容加入易错点章节。这是迭代改进技能最直接的方法之一（参见[通过实际执行持续改进](#refine-with-real-execution)）。
</Tip>

### 输出格式模板 [#templates-for-output-format]

需要智能体以特定格式生成输出时，请提供模板。这比用文字描述格式更可靠，因为智能体善于匹配具体结构。短模板可以直接放在 `SKILL.md` 中；较长或仅在特定情况下需要的模板，应存入 `assets/`，再从 `SKILL.md` 中引用，以便只在需要时加载。

````markdown
## 报告结构

使用以下模板，并根据具体分析按需调整章节：

```markdown
# [分析标题]

## 执行摘要
[用一段话概述主要发现]

## 主要发现
- 发现 1 及其支撑数据
- 发现 2 及其支撑数据

## 建议
1. 具体且可执行的建议
2. 具体且可执行的建议
```
````

### 多步骤工作流检查清单 [#checklists-for-multi-step-workflows]

明确的检查清单有助于智能体跟踪进度并避免遗漏步骤，尤其适合具有依赖关系或验证关卡的步骤。

```markdown
## 表单处理工作流

进度：
- [ ] 步骤 1：分析表单（运行 `scripts/analyze_form.py`）
- [ ] 步骤 2：创建字段映射（编辑 `fields.json`）
- [ ] 步骤 3：验证映射（运行 `scripts/validate_fields.py`）
- [ ] 步骤 4：填写表单（运行 `scripts/fill_form.py`）
- [ ] 步骤 5：验证输出（运行 `scripts/verify_output.py`）
```

### 验证循环 [#validation-loops]

要求智能体在继续之前验证自己的工作。该模式是：完成工作，运行验证器（脚本、参考检查清单或自检），修复所有问题，然后重复，直到验证通过。

```markdown
## 编辑工作流

1. 完成编辑
2. 运行验证：`python scripts/validate.py output/`
3. 如果验证失败：
   - 查看错误消息
   - 修复问题
   - 再次运行验证
4. 只有验证通过后才能继续
```

参考文档也可以充当“验证器”：要求智能体在最终完成前对照参考文档检查工作。

### 计划—验证—执行 [#plan-validate-execute]

对于批量或破坏性操作，应让智能体先以结构化格式创建中间计划，对照事实来源验证计划，然后再执行。

```markdown
## PDF 表单填写

1. 提取表单字段：`python scripts/analyze_form.py input.pdf` → `form_fields.json`
   （列出每个字段的名称、类型以及是否必填）
2. 创建 `field_values.json`，将每个字段名称映射到预期值
3. 验证：`python scripts/validate_fields.py form_fields.json field_values.json`
   （检查每个字段名称是否存在于表单中、类型是否兼容以及是否遗漏必填字段）
4. 如果验证失败，修改 `field_values.json` 并重新验证
5. 填写表单：`python scripts/fill_form.py input.pdf field_values.json output.pdf`
```

其中的关键是步骤 3：验证脚本会对照事实来源（`form_fields.json`）检查计划（`field_values.json`）。像“找不到字段 'signature_date'——可用字段：customer_name、order_total、signature_date_signed”这样的错误能为智能体提供足够的信息，使其自行纠正。

### 附带可复用脚本 [#bundling-reusable-scripts]

[迭代改进技能](/skill-creation/evaluating-skills)时，请比较智能体在不同测试用例中的执行轨迹。如果发现智能体每次运行都在独立地重新实现同一套逻辑，例如生成图表、解析特定格式或验证输出，就应该编写一个经过测试的脚本，并把它放入 `scripts/` 中。

有关设计和附带脚本的更多信息，请参阅[在技能中使用脚本](/skill-creation/using-scripts)。
