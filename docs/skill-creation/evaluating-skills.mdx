你编写了一个技能，用一条提示词试过，看起来可以工作。但它在不同提示词和边界情况下是否始终可靠？与完全不使用技能相比是否更好？运行结构化评估（eval）能够回答这些问题，并建立反馈循环，帮助你系统地改进技能。

## 设计测试用例 [#designing-test-cases]

一个测试用例包含三个部分：

- **提示词**：真实的用户消息，也就是用户实际可能输入的内容。
- **预期输出**：便于人类阅读的成功标准说明。
- **输入文件**（可选）：技能处理任务所需的文件。

将测试用例存储在技能目录内的 `evals/evals.json` 中：

```json evals/evals.json
{
  "skill_name": "csv-analyzer",
  "evals": [
    {
      "id": 1,
      "prompt": "data/sales_2025.csv 中有一份月度销售数据。请找出收入最高的 3 个月并制作条形图。",
      "expected_output": "一张展示收入最高 3 个月的条形图，包含坐标轴标签和数值。",
      "files": ["evals/files/sales_2025.csv"]
    },
    {
      "id": 2,
      "prompt": "下载目录里有个 customers.csv，有些行缺少邮箱——请清理一下，并告诉我一共有多少处缺失。",
      "expected_output": "一份已处理缺失邮箱的干净 CSV，以及缺失数量统计。",
      "files": ["evals/files/customers.csv"]
    }
  ]
}
```

**编写优质测试提示词的技巧：**

- **先从 2—3 个测试用例开始。** 在看到第一轮结果前不要投入过多，之后可以再扩充测试集。
- **改变提示词。** 使用不同措辞、详细程度和正式程度。有些提示词应当口语化（“嘿，能帮我清理一下这个 csv 吗”），另一些则应精确（“解析 data/input.csv，删除 B 列为空的行，并将结果写入 data/output.csv”）。
- **覆盖边界情况。** 至少包含一条测试边界条件的提示词，例如格式错误的输入、不寻常的请求，或技能指令可能存在歧义的情况。
- **使用真实上下文。** 真实用户会提到文件路径、列名和个人背景。“处理这些数据”之类的提示词过于模糊，无法进行有效测试。

暂时无需定义具体的通过/失败检查，只需准备提示词和预期输出。看到第一轮运行结果后，再加入详细检查（称为断言）。

## 运行评估 [#running-evals]

核心模式是让每个测试用例运行两次：一次**使用技能**，另一次**不使用技能**（或使用上一版本）。这样就有了可供比较的基线。

### 工作区结构 [#workspace-structure]

在技能目录旁创建工作区目录来组织评估结果。每次完整执行评估循环，都使用独立的 `iteration-N/` 目录。目录内每个测试用例都有一个评估目录，其中包含 `with_skill/` 和 `without_skill/` 子目录：

```
csv-analyzer/
├── SKILL.md
└── evals/
    └── evals.json
csv-analyzer-workspace/
└── iteration-1/
    ├── eval-top-months-chart/
    │   ├── with_skill/
    │   │   ├── outputs/       # 本次运行生成的文件
    │   │   ├── timing.json    # token 数和耗时
    │   │   └── grading.json   # 断言结果
    │   └── without_skill/
    │       ├── outputs/
    │       ├── timing.json
    │       └── grading.json
    ├── eval-clean-missing-emails/
    │   ├── with_skill/
    │   │   ├── outputs/
    │   │   ├── timing.json
    │   │   └── grading.json
    │   └── without_skill/
    │       ├── outputs/
    │       ├── timing.json
    │       └── grading.json
    └── benchmark.json         # 汇总统计
```

主要由你手动编写的文件是 `evals/evals.json`。其他 JSON 文件（`grading.json`、`timing.json`、`benchmark.json`）在评估过程中由智能体、脚本或你生成。

### 启动各次运行 [#spawning-runs]

每次评估运行都应从干净的上下文开始，不要保留上一次运行或技能开发过程中的状态。这样才能确保智能体只遵循 `SKILL.md` 中的内容。在支持子智能体的环境中（例如 Claude Code），每项子任务都会从全新上下文开始，自然具备这种隔离性。如果环境不支持子智能体，请为每次运行使用单独的会话。

每次运行需要提供：

- 技能路径（基线运行则不提供技能）
- 测试提示词
- 所有输入文件
- 输出目录

下面是一组提供给智能体的“使用技能”单次运行指令示例：

```
执行此任务：
- 技能路径：/path/to/csv-analyzer
- 任务：data/sales_2025.csv 中有一份月度销售数据。
  请找出收入最高的 3 个月并制作条形图。
- 输入文件：evals/files/sales_2025.csv
- 将输出保存到：csv-analyzer-workspace/iteration-1/eval-top-months-chart/with_skill/outputs/
```

对于基线运行，请使用相同提示词，但不提供技能路径，并将结果保存到 `without_skill/outputs/`。

改进现有技能时，请把上一版本作为基线。编辑前先创建快照（`cp -r <skill-path> <workspace>/skill-snapshot/`），让基线运行使用该快照，并将结果保存到 `old_skill/outputs/`，而不是 `without_skill/`。

### 记录计时数据 [#capturing-timing-data]

计时数据可以比较技能相对于基线所需的时间和 token。一项技能如果能显著提高输出质量、但 token 用量增加三倍，与一项效果更好且成本更低的技能有着不同的权衡。每次运行完成后，请记录 token 数和耗时：

```json timing.json
{
  "total_tokens": 84852,
  "duration_ms": 23332
}
```

<Tip>
在 Claude Code 中，子智能体任务完成时，[任务完成通知](https://platform.claude.com/docs/en/agent-sdk/typescript#sdk-task-notification-message)会包含 `total_tokens` 和 `duration_ms`。请立即保存这些值，因为它们不会在其他地方持久化。
</Tip>

## 编写断言 [#writing-assertions]

断言是关于输出应包含或实现什么的可验证陈述。请在看到第一轮输出后再添加断言，因为在技能实际运行前，你往往并不知道什么才算“好”。

优质断言：

- `"输出文件是有效的 JSON"`——可通过程序验证。
- `"条形图的坐标轴带有标签"`——具体且可观察。
- `"报告至少包含 3 条建议"`——可以计数。

较弱的断言：

- `"输出很好"`——过于模糊，无法评分。
- `"输出必须逐字使用短语 '总收入：$X'"`——过于脆弱；措辞不同但内容正确的输出也会失败。

不是所有质量都需要断言。写作风格、视觉设计、输出是否“感觉合适”等特征，很难拆解成通过/失败检查，更适合在[人工审查](#reviewing-results-with-a-human)中发现。断言应留给能够客观检查的内容。

将断言添加到 `evals/evals.json` 中的各个测试用例：

```json evals/evals.json highlight={9-14}
{
  "skill_name": "csv-analyzer",
  "evals": [
    {
      "id": 1,
      "prompt": "data/sales_2025.csv 中有一份月度销售数据。请找出收入最高的 3 个月并制作条形图。",
      "expected_output": "一张展示收入最高 3 个月的条形图，包含坐标轴标签和数值。",
      "files": ["evals/files/sales_2025.csv"],
      "assertions": [
        "输出包含一个条形图图像文件",
        "图表恰好展示 3 个月",
        "两个坐标轴都有标签",
        "图表标题或说明中提到收入"
      ]
    }
  ]
}
```

## 为输出评分 [#grading-outputs]

评分是根据实际输出评估每条断言，并使用具体证据记录**通过（PASS）**或**失败（FAIL）**。证据应引用或指向输出，而不是只表达观点。

最简单的方法是把输出和断言交给 LLM，让它逐条评估。对于可以用代码检查的断言（JSON 是否有效、行数是否正确、文件是否存在且尺寸符合预期），应使用验证脚本；脚本在机械检查上比 LLM 判断更可靠，而且能够跨迭代复用。

```json grading.json
{
  "assertion_results": [
    {
      "text": "输出包含一个条形图图像文件",
      "passed": true,
      "evidence": "在 outputs 目录中找到 chart.png（45KB）"
    },
    {
      "text": "图表恰好展示 3 个月",
      "passed": true,
      "evidence": "图表包含三月、七月和十一月的条形"
    },
    {
      "text": "两个坐标轴都有标签",
      "passed": false,
      "evidence": "Y 轴标记为‘收入（$）’，但 X 轴没有标签"
    },
    {
      "text": "图表标题或说明中提到收入",
      "passed": true,
      "evidence": "图表标题为‘收入最高的 3 个月’"
    }
  ],
  "summary": {
    "passed": 3,
    "failed": 1,
    "total": 4,
    "pass_rate": 0.75
  }
}
```

### 评分原则 [#grading-principles]

- **只有具体证据才能判定为通过。** 不要在证据不足时作有利推断。如果断言要求“包含摘要”，而输出只有一个标题为“摘要”的章节和一句模糊的话，则应判定为失败——标签虽然存在，但内容不足。
- **不仅要审查结果，也要审查断言本身。** 评分时注意断言是否过于简单（无论技能质量如何总会通过）、过于困难（即使输出很好也总会失败）或无法验证（仅凭输出无法检查）。请在下一轮迭代中修正这些断言。

<Tip>
比较两个技能版本时，可以尝试**盲测比较**：把两份输出交给 LLM 评委，但不透露各自来自哪个版本。评委使用自己的评分标准评价组织、格式、可用性和完成度等整体质量，不会受到“哪个版本理应更好”的偏见影响。这能补充断言评分：两份输出可能都通过全部断言，但整体质量仍有明显差异。
</Tip>

## 汇总结果 [#aggregating-results]

本轮迭代中的每次运行都完成评分后，请计算每种配置的汇总统计，并将结果保存到评估目录旁的 `benchmark.json`（例如 `csv-analyzer-workspace/iteration-1/benchmark.json`）：

```json benchmark.json
{
  "run_summary": {
    "with_skill": {
      "pass_rate": { "mean": 0.83, "stddev": 0.06 },
      "time_seconds": { "mean": 45.0, "stddev": 12.0 },
      "tokens": { "mean": 3800, "stddev": 400 }
    },
    "without_skill": {
      "pass_rate": { "mean": 0.33, "stddev": 0.10 },
      "time_seconds": { "mean": 32.0, "stddev": 8.0 },
      "tokens": { "mean": 2100, "stddev": 300 }
    },
    "delta": {
      "pass_rate": 0.50,
      "time_seconds": 13.0,
      "tokens": 1700
    }
  }
}
```

`delta` 表示技能付出的成本（更多时间和 token）以及获得的收益（更高的通过率）。一项技能增加 13 秒却把通过率提高 50 个百分点，通常值得采用；如果 token 用量翻倍却只提高 2 个百分点，可能并不划算。

<Note>
标准差（`stddev`）只有在每项评估运行多次时才有意义。在只有 2—3 个测试用例且各运行一次的早期迭代中，请重点关注原始通过数量和差值。随着测试集扩大、每项评估运行多次，统计指标才会变得有用。
</Note>

## 分析规律 [#analyzing-patterns]

汇总统计可能掩盖重要规律。计算基准后：

- **删除或替换在两种配置中都始终通过的断言。** 这些断言不能提供有用信息，因为模型没有技能也能妥善处理。它们会抬高使用技能时的通过率，却没有反映技能的实际价值。
- **调查在两种配置中都始终失败的断言。** 可能是断言本身有问题（要求模型完成其无法完成的事情）、测试用例太难，或者断言检查了错误目标。请在下一轮迭代前修复。
- **研究使用技能时通过、不使用时失败的断言。** 这些地方清楚地体现了技能的价值。请理解*为什么*会有差异：是哪些指令或脚本产生了作用？
- **当不同运行的结果不一致时收紧指令。** 如果同一评估有时通过、有时失败（在基准中表现为较高的 `stddev`），可能是评估容易波动（对模型随机性敏感），也可能是技能指令存在歧义，导致模型每次的理解不同。请增加示例或更具体的指导来减少歧义。
- **检查时间和 token 异常值。** 如果某项评估耗时是其他项的 3 倍，请阅读执行记录（模型在运行期间所做操作的完整日志）来寻找瓶颈。

## 由人工审查结果 [#reviewing-results-with-a-human]

断言评分和规律分析能够发现很多问题，但它们只会检查你想到并写成断言的内容。人工审查者能带来新的视角，发现未曾预料的问题、注意到技术上正确却偏离目标的输出，或者识别难以表示为通过/失败检查的问题。请针对每个测试用例，将实际输出与评分放在一起审查。

为每个测试用例记录具体反馈并保存在工作区中，例如在评估目录旁保存为 `feedback.json`：

```json feedback.json
{
  "eval-top-months-chart": "图表缺少坐标轴标签，而且月份按字母顺序而不是时间顺序排列。",
  "eval-clean-missing-emails": ""
}
```

“图表缺少坐标轴标签”是可执行的反馈；“看起来很差”则不是。反馈为空表示输出看起来没有问题，该测试用例已通过审查。在[迭代步骤](#iterating-on-the-skill)中，请重点改进收到具体意见的测试用例。

## 迭代改进技能 [#iterating-on-the-skill]

评分和审查完成后，你会获得三类信号：

- **失败的断言**指出具体缺口，例如缺少步骤、指令不清楚或技能未处理某种情况。
- **人工反馈**指出更广泛的质量问题，例如方法错误、输出结构不佳，或结果技术上正确却没有帮助。
- **执行记录**揭示问题*为什么*发生。如果智能体忽略了一条指令，该指令可能存在歧义；如果智能体花时间执行无效步骤，相关指令可能需要简化或删除。

把这三类信号与当前 `SKILL.md` 一并交给 LLM，让它提出修改建议，是将信号转化为技能改进最有效的方法。LLM 能够归纳失败断言、审查意见和执行行为之间的规律，省去繁琐的人工关联。提示 LLM 时，请加入以下指导：

- **从反馈中泛化。** 技能将用于许多不同提示词，而不只是测试用例。修复应广泛解决底层问题，不要为具体示例添加狭窄补丁。
- **保持技能精简。** 更少但更好的指令，往往优于详尽的规则。如果执行记录显示存在无效工作（不必要的验证或中间输出），请删除相关指令。如果不断增加规则但通过率停滞，技能可能受到了过多约束；尝试删除一些指令，看看结果能否保持或改善。
- **解释原因。** 基于推理的指令（“执行 X，因为 Y 容易导致 Z”）优于僵硬命令（“始终执行 X，绝不执行 Y”）。模型理解指令目的后，通常会更可靠地遵循指令。
- **附带重复工作。** 如果每次测试运行都各自编写了相似的辅助脚本（图表生成器、数据解析器），就应该把该脚本放进技能的 `scripts/` 目录。有关方法，请参阅[使用脚本](/skill-creation/using-scripts)。

### 循环 [#the-loop]

1. 将评估信号和当前 `SKILL.md` 交给 LLM，让它提出改进建议。
2. 审查并应用修改。
3. 在新的 `iteration-<N+1>/` 目录中重新运行所有测试用例。
4. 为新结果评分并进行汇总。
5. 由人工审查，然后重复。

当结果令人满意、反馈始终为空，或各轮迭代之间不再有明显改进时，即可停止。

<Tip>
[`skill-creator`](https://github.com/anthropics/skills/tree/main/skills/skill-creator) 技能可以自动完成此工作流的大部分内容，包括运行评估、为断言评分、汇总基准，以及展示结果供人工审查。
</Tip>
